# Lumenpulse API Integration Guide

## 1. Purpose

This document is the narrative reference for any outside developer or ecosystem partner
building on top of the Lumenpulse backend. It explains how to authenticate, which
environments and base URLs to target, how pagination and standard errors work, the
rate limits per endpoint class and how to handle them, which endpoints are stable
enough to rely on, and — finally — it walks end-to-end through fetching a project
and its current funding state.

> **Swagger / OpenAPI:** The machine-readable spec and "try-it" UI is generated by
> NestJS Swagger on every running backend instance at
> `<base-url>/api/docs` (see §2.2 for base URLs per environment). That page also
> documents every DTO and includes `@nestjs/swagger` examples. Use this guide for
> narrative and conventions; use Swagger for per-route parameter details and the
> exact request/response schemas.

## 2. Base URLs, Environments, and Obtaining Credentials

### 2.1 Environments and base URLs

Swagger declares two servers in `apps/backend/src/main.ts`; partners may also run
a local backend against testnet for development.

| Name        | Base URL                           | Stellar network | Who needs it?                              |
|-------------|------------------------------------|-----------------|--------------------------------------------|
| Local Dev   | `http://localhost:3000` (default)  | Testnet (configurable) | Developers running `npm start:dev` |
| Development (shared) | No shared host yet          | Testnet         | Lumenpulse internal + trusted 3rd parties  |
| Production  | `https://api.lumenpulse.io`       | Public Network  | All live production integrations           |

Path prefixes:
- All endpoints live under the root. Versioned endpoints use URI versioning:
  e.g. `GET /v1/config/stellar`.
- Swagger UI and the generated JSON spec:
  - `GET /api/docs` → interactive Swagger UI
  - `GET /api/docs-json` → raw OpenAPI 3 JSON (if needed for codegen tools)

Before writing any integration code, call `GET /health` and
`GET /v1/config/stellar` — they are public and tell you the instance is reachable
and which Stellar network + contract addresses it is configured for.

```bash
# Quick sanity check against local backend
curl -s http://localhost:3000/health | jq .
```

```json
{
  "status": "ok",
  "details": { "database": "up", "redis": "up" },
  "error": null,
  "info": { "database": { "status": "up" }, "redis": { "status": "up" } }
}
```

### 2.2 Getting credentials

There are two ways an API caller obtains identity in the Lumenpulse backend.

#### 2.2.1 Username + password (human users, JWT access tokens)

Used by the webapp and mobile apps. Machine-to-machine partners should generally
use method 2.2.2 instead.

```bash
# 1. Register a new account (unthrottled profile in DEV; see §5 for limits)
curl -X POST http://localhost:3000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{ "email": "bot@partner.example", "password": "correct horse battery staple" }'
```

```json
{
  "id": "0a9c0f5e-8a2e-4c5a-9e73-9c5f6d1c2d67",
  "email": "bot@partner.example",
  "createdAt": "2026-08-27T10:00:00.000Z"
}
```

Then exchange the credentials for tokens:

```bash
curl -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{ "email": "bot@partner.example", "password": "correct horse battery staple" }'
```

Possible responses:
- **No 2FA configured →** tokens issued directly.
- **2FA enabled →** you first receive `{ requiresTwoFactor: true }`, then call
  `POST /auth/2fa/verify` with the email, password, and 6-digit TOTP code.

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIwYTljMGY1ZS04YTJlLTRjNWEtOWU3My05YzVmNmQxYzJkNjciLCJlbWFpbCI6ImJvdHBhcnRuZXIuZXhhbXBsZSIsImlhdCI6MTcwMzY4MzYyMCwiZXhwIjoxNzAzNjg3MjIwfQ.signed",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.signed.refresh.payload"
}
```

Token lifecycle:
- `access_token` → short-lived (default 1 hour, configurable via `JWT_EXPIRES_IN`).
  Send on every subsequent request as `Authorization: Bearer <access_token>`.
- `refresh_token` → long-lived (30 days, stored in DB with IP + device info).
  Call `POST /auth/refresh { refreshToken }` to rotate the pair; call
  `POST /auth/logout { refreshToken }` to revoke a specific token, or
  `POST /auth/logout-all` (requires valid access token) to wipe all sessions.
- Session management endpoints: `GET /auth/sessions` (list with device info),
  `POST /auth/sessions/:id/revoke`. All guarded by the access token.

#### 2.2.2 Stellar wallet authentication (machine-to-machine, dApp users)

Preferred for integration partners and any automated system that already holds a
Stellar keypair. The backend issues a SEP-10-style challenge, the caller signs it
with their wallet, and the backend returns a JWT tied to the public key.

```bash
# 1. Request a challenge (public, rate-limited as auth-class)
curl "http://localhost:3000/auth/challenge?publicKey=GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN"
```

```json
{
  "challenge": "AAAAAgAAAAB…<signed XDR challenge envelope>…",
  "nonce": "n84hf02h5t6",
  "expiresIn": 300
}
```

Sign the returned challenge XDR with the matching secret key. How you do this
depends on your SDK/language (Freighter, Lobstr, `stellar-sdk`, etc.). The
`@stellar/stellar-sdk` JS pattern is roughly:

```ts
import { Keypair, Transaction } from '@stellar/stellar-sdk';

const kp = Keypair.fromSecret('S…secret');
const tx = TransactionBuilder.fromXDR(challenge, Networks.TESTNET);
tx.sign(kp);
const signedChallenge = tx.toXDR();
```

Then post the signed payload back:

```bash
curl -X POST http://localhost:3000/auth/verify \
  -H 'Content-Type: application/json' \
  -d '{
    "publicKey": "GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN",
    "signedChallenge": "AAAAAgAAAAB…<signed XDR>…"
  }'
```

```json
{
  "success": true,
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.wallet-signed-token.payload",
  "user": {
    "id": "2f6e4d1a-b0c9-4b7e-938c-47a1c10c3c0a",
    "stellarPublicKey": "GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN"
  }
}
```

Use the returned `token` exactly like a password-login `access_token`:
`Authorization: Bearer <token>`. The JWT `sub` claim is the user id; the stellar
public key is available both in the user object returned by `/auth/verify` and
via `GET /auth/profile` (`stellarPublicKey` field).

#### 2.2.3 API key header (optional tracking dimension)

`RATE_LIMIT_TRACK_BY_API_KEY` can be flipped on per environment (see
`apps/backend/src/common/rate-limit/rate-limit.config.ts`). When enabled, callers
may also send an `X-API-Key` header (configurable name via
`RATE_LIMIT_API_KEY_HEADER`). This does **not** authenticate the caller — the JWT
`Authorization` header is still required on protected routes — but it replaces the
client IP address as the rate-limit key identity, which matters for partners
sharing an egress IP. Contact the Lumenpulse team to have a long-lived API key
issued for your service; the key is used only for tracking/billing and never for
auth on its own.

### 2.3 2FA (TOTP) enable/disable

Once a user is authenticated via JWT, they can optionally enable TOTP 2FA:
- `POST /auth/2fa/generate` → returns `{ secret, qrCode }`. The `qrCode` is a
  data URI ready to render in an `<img>` tag; the `secret` is the TOTP base32
  seed for authenticator apps that don't scan QR codes.
- `POST /auth/2fa/enable { token }` → once the user confirms a valid 6-digit TOTP,
  2FA is enabled. Subsequent logins follow the 2FA step described in §2.2.1.
- `POST /auth/2fa/disable { token }` → reverts login back to single-factor.

## 3. Pagination and Filtering

The backend exposes two pagination styles. Callers must follow the style of each
individual route; routes never silently fall back between them.

### 3.1 Style A — Page-number / offset pagination

Used by most business-list endpoints: projects, contributor-feed, grants
leaderboard, etc. Query parameters:

| Param       | Type   | Default | Min / Max | Notes                                 |
|-------------|--------|---------|-----------|---------------------------------------|
| `page`      | number | 1       | 1+        | 1-indexed. Omitting = page 1.         |
| `limit`     | number | 10 / 20 | 1–100     | Hard cap of 100; larger values are clamped or rejected. |
| `sortBy`    | string | varies  | —         | Allowed fields are per-route; Swagger lists them. |
| `sortOrder` | string | `DESC`  | `ASC` / `DESC` | Case-insensitive.                  |

Response envelope (example from `ProjectListResponseDto`):

```json
{
  "projects": [
    {
      "projectId": "project_42",
      "owner": "GDE…OWNER",
      "metadata": { "name": "Solar Panel Crowdfund", "tags": ["climate"] },
      "onChainStatus": {
        "status": "active",
        "vault": { "totalDeposited": "120000000", "currentBalance": "98000000", "contributorCount": 17 }
      },
      "createdAt": "2026-08-01T00:00:00.000Z"
    }
  ],
  "total": 143,
  "page": 1,
  "limit": 10,
  "totalPages": 15
}
```

Conventions that are **always true** for style A:
- The array key name is plural and describes the items (e.g. `projects`, `entries`,
  `sessions`, `contributions`).
- `total` is the total number of items across all pages before filtering was
  applied — you can rely on `Math.ceil(total / limit) === totalPages`.
- Empty pages are NOT 404s; they return the envelope with `[]` and `total = 0`.

Worked pagination loop:

```ts
async function listAllProjects(baseUrl: string, jwt: string) {
  const projects = [];
  let page = 1;
  while (true) {
    const url = `${baseUrl}/projects?page=${page}&limit=100`;
    const res = await fetch(url, { headers: { Authorization: `Bearer ${jwt}` } });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const body = (await res.json()) as {
      projects: unknown[]; total: number; totalPages: number; page: number;
    };
    projects.push(...body.projects);
    if (body.page >= body.totalPages) break;
    page += 1;
  }
  return projects;
}
```

### 3.2 Style B — Cursor / asset-discovery pagination

Used by endpoints that stream rows ordered by a non-stable key, notably the
Stellar asset search (`AssetDiscoveryQueryDto`) family.

| Param       | Type   | Default | Notes                                              |
|-------------|--------|---------|----------------------------------------------------|
| `limit`     | number | 10      | Max 100.                                           |
| `cursor`    | string | absent  | Send the `nextCursor` returned by the previous page. Omit on first call. |

Response envelope:

```json
{
  "assets": [ { "assetCode": "USDC", "assetIssuer": "GA5Z…", "assetType": "credit_alphanum4" } ],
  "nextCursor": "123456789",
  "hasMore": true,
  "total": 452
}
```

Follow the cursor loop until `hasMore === false` OR `nextCursor` is absent:

```bash
# First page
curl -s 'http://localhost:3000/search/assets?q=USD&limit=100'
# → take .nextCursor = "123456789"

# Second page
curl -s 'http://localhost:3000/search/assets?q=USD&limit=100&cursor=123456789'
```

### 3.3 Filtering patterns

Filtering always uses top-level query parameters — the backend never uses the
`filter[field]` nested bracket style. Common parameters across routes:

| Where it applies          | Param        | Type   | Example                 |
|---------------------------|--------------|--------|-------------------------|
| `/projects`               | `status`     | enum   | `ACTIVE`, `COMPLETED`, `EXPIRED`, `CANCELLED` |
| `/projects`               | `owner`      | string | Stellar address `G…`    |
| `/news`                   | `tag`        | string | e.g. `stellar`          |
| `/news`                   | `category`   | string | e.g. `DeFi`             |
| `/news`                   | `lang`       | string | ISO 639-1, e.g. `EN`    |
| `/news/search`            | `q`, `source`| string | keyword + source key    |
| `/news/coin/:symbol`      | `:symbol`    | string | path param, e.g. `BTC`  |
| `/news/categories`        | `status`     | enum   | `ACTIVE` / `INACTIVE` / `ALL` |
| `/grants/leaderboard`     | `roundId`    | number | **required**            |
| `/grants/leaderboard`     | `topN`       | number | Optional top-N, disables page pagination when set |
| `/contributor-feed`       | `activityType` | enum | `REGISTRATION` / `CONTRIBUTION` / `REPUTATION` |
| `/contributor-feed`       | `contributorAddress` | string | Stellar address     |
| `/search/assets`          | `assetCode`, `issuer`, `q`, `minAccounts`, `maxAccounts` | — | exact + partial filters |
| `/search/assets`          | `sort`       | enum   | `relevance` (default) or `accounts` |

If a parameter is provided with an invalid value (e.g. `?sort=price` on an
endpoint that only supports `relevance`/`accounts`), the response follows the
standard validation-error shape in §4.

## 4. Standard Error Response Shape

Every 4xx and 5xx response produced by the backend passes through the
`GlobalExceptionFilter` (`apps/backend/src/filters/global-exception.filter.ts`).
The shape is **always**:

```ts
interface ErrorResponse {
  code: string;           // Machine-readable error code (see §4.2)
  message: string;        // Human-readable English message
  details?:               // Optional structured detail (array or object)
    | Array<{ field?: string; message: string }>
    | Record<string, unknown>;
  requestId: string;      // Value of the X-Request-Id header for support
}
```

Corresponding HTTP semantics:
- A `X-Request-Id: <value>` response header is set on EVERY response, success or
  error, matching the body `requestId` field. If you need support, quote this ID.
- In production, 5xx responses generated from uncaught `Error` objects have their
  `message` replaced with the fixed string `"Internal server error"` to prevent
  leaking stack traces / connection strings. The `requestId` still lets
  Lumenpulse engineers trace the real message in logs.

### 4.1 Worked examples

Validation failure:

```bash
curl -i -X POST http://localhost:3000/auth/login \

  -d '{ "email": "not-an-email", "password": "x" }'
```

### 4.2 Error code index (top-level namespaces)

Every code is `<NAMESPACE>_<NNN>`. The full current enum is in
`apps/backend/src/common/enums/error-code.enum.ts`:

| Namespace | Prefix  | Category                                            |
|-----------|---------|-----------------------------------------------------|
| AUTH      | AUTH_001–007 | JWT, credentials, 2FA, disabled users          |
| System    | SYS_001–011  | 5xx, validation, not found, forbidden, rate limit, conflict, media type, payload too large |
| User      | USER_001–003 | Users-specific 404 / already exists              |
| Stellar   | STEL_001–010 | Wallet, balance, simulation, RPC, friendbot      |
| Treasury  | TREAS_001–011 | Treasury stream + multisig                        |
| Vesting   | VEST_001–011  | Vesting wallet streams                             |
| Analytics | ANLY_001–003  | Sentiment, news sync, data not found               |

Clients SHOULD branch on `code`, never on `message`; `message` is free-form text
for humans and may be improved without notice.

## 5. Rate Limits, Retry, and Backoff

All limits live in `apps/backend/src/common/rate-limit/rate-limit.config.ts` and
are enforced by `@nestjs/throttler` backed by shared Redis when configured. Every
endpoint is assigned to exactly one class (plus a global catch-all). The class name
is also the override exported from the config file (e.g. `getAuthThrottleOverride`)
applied via `@Throttle(...)` on the controller.

### 5.1 Classes and per-environment limits

Limits are expressed as `limit` hits per `ttl` millisecond window, followed by an
additional `blockDuration` ms ban on any client that hits the limit.

| Class                   | Override helper                         | DEV (req / window / block) | STAGING | PROD  |
|-------------------------|-----------------------------------------|:--------------------------:|:-------:|:-----:|
| **Global default**      | `default` throttler                     |  300 / 60 s / 60 s         | 180 / 60 s / 60 s | 120 / 60 s / 60 s |
| **Auth** (login, register, refresh, 2fa verify, verify challenge) | `getAuthThrottleOverride` | 15 / 60 s / 300 s | 10 / 60 s / 300 s | 8 / 60 s / 300 s |
| **Portfolio read**      | `getPortfolioReadThrottleOverride`      | 180 / 60 s / 60 s          | 120     | 90    |
| **Portfolio write**     | `getPortfolioWriteThrottleOverride`     |  20 / 60 s / 120 s         | 12      | 10    |
| **Watchlist read**      | `getWatchlistReadThrottleOverride`      | 200 / 60 s / 60 s          | 150     | 100   |
| **Watchlist write**     | `getWatchlistWriteThrottleOverride`     |  30 / 60 s / 120 s         | 20      | 15    |
| **News read**           | `getNewsReadThrottleOverride`           | 120 / 60 s / 60 s          | 80      | 60    |
| **Project read**        | `getProjectReadThrottleOverride`        | 100 / 60 s / 60 s          | 60      | 40    |
| **Crowdfund read**      | `getCrowdfundReadThrottleOverride`      | 100 / 60 s / 60 s          | 60      | 40    |
| **Stellar read**        | `getStellarReadThrottleOverride`        |  60 / 60 s / 60 s          | 40      | 30    |
| **Search read**         | `getSearchReadThrottleOverride`         |  60 / 60 s / 60 s          | 40      | 30    |
| **Analytics read**      | `getAnalyticsReadThrottleOverride`      |  60 / 60 s / 60 s          | 40      | 30    |
| **Friendbot bootstrap** | `getFriendbotBootstrapThrottleOverride` |   5 / 1 h / 1 h            | 3 / 1 h | 2 / 1 h |
| **Registry read**       | `getRegistryReadThrottleOverride`       | same as Crowdfund read    | same    | same  |
| **Registry write**      | `getRegistryWriteThrottleOverride`      | same as Portfolio write   | same    | same  |

Contributors also set these per-environment at runtime via environment variables
named `RATE_LIMIT_<UPPER_SNAKE_CLASS>_LIMIT`, `_TTL_MS`, `_BLOCK_MS` (see the
config file for the full list).

### 5.2 How rate-limit identity is tracked

The tracker builds an identity key from up to two sources, in order:
1. If `RATE_LIMIT_TRACK_BY_API_KEY=true` AND the caller sends `X-API-Key`, the key
   value is prefixed with `api-key:<value>`.
2. If `RATE_LIMIT_TRACK_BY_IP=true` (the default), OR nothing else matched, the
   client IP is added as `ip:<address>`.

Therefore, a partner behind a shared NAT should request an API key (see §2.2.3)
to avoid being rate-limited alongside unrelated traffic from the same IP.

### 5.3 Retry and backoff behaviour

When you receive HTTP `429 Too Many Requests`:

1. Always read the `Retry-After` response header. It contains the integer number
   of seconds remaining until the block expires. Do NOT issue new requests for that
   class until `Retry-After` seconds have elapsed.
2. If `Retry-After` is absent (only happens on the global default class in very
   old deployments), fall back to exponential backoff starting at 1 s, capped at
   32 s, with ±25 % jitter. A well-tested algorithm is "decorrelated jitter":

   ```ts
   function nextDelay(prev: number, base = 1_000, cap = 32_000): number {
     const newDelay = Math.min(cap, Math.random() * (prev * 3 - base) + base);
     return newDelay;
   }
   ```

When you receive HTTP `5xx`, `408 Request Timeout`, or `STEL_006` / `STEL_007`
(Soroban RPC timeout / unavailable):
- Retry the request **if and only if** the request is known safe to retry (GET or
  an idempotent write that includes the `Idempotency-Key` header — see the
  idempotency spec). Do NOT blindly retry POST mutation endpoints without an
  idempotency key; you risk double-charging or double-contributing.
- Retry count: max 3 attempts total. After 3, surface the error to the operator
  and/or queue the item for human review.
- For `STEL_006 / STEL_007`, wait at least 3 s before the first retry so the
  Soroban RPC endpoint can recover; do not slam the RPC with retries every 100 ms.

## 6. Stability Classification of Endpoints

Every endpoint / tag in the backend is classified as one of:

- **STABLE —** Public, documented, committed to backwards compatibility within a
  URI version (e.g. `/v1/**`). Breaking changes introduce a new URI version.
- **BETA —** Public, intended for early partners; contract may still change in
  backwards-incompatible ways with a one-release deprecation window.
- **INTERNAL —** Used by the Lumenpulse webapp, mobile app, or admin dashboards
  only. No compatibility guarantees; partners should not rely on these routes.

Partners **must only build on STABLE routes**. If you need something that is
currently BETA or INTERNAL, open a request to promote it; promotion means
adding E2E tests, a stability tag in Swagger, and a review of the response
shape so it can carry the same `/v1` compatibility promise as the stable routes.

| `feature-flags`         | `/feature-flags/**`      | **INTERNAL** | Bearer JWT — admin | Global default |
| `metrics`               | `/metrics/**`            | **INTERNAL** | IP allowlist (no JWT) | Global default + IP ACL |
| `app`                   | `GET /`                  | **STABLE** | No  | Global default |

### 6.2 Compatibility rules for STABLE endpoints

- Adding a new optional request field or a new response field is NOT a breaking
  change; consumers must ignore unknown keys (JSON is self-describing).
- Renaming or removing fields, changing the type of a field, or tightening
  validation on request parameters **is** a breaking change — it goes into
  `/v2/<route>` and the old `/v1/<route>` continues to function for at least
  two release cycles with deprecation warnings in the response.
- URI versions are declared only where needed. Today only `/v1/config/*` carries
  a version prefix; the remaining STABLE routes live at the root and implicitly
  define `/v1`. When a second version is introduced, all stable routes will
  receive the `/v1/` prefix alias for consistency.

## 7. End-to-End Worked Example: Fetch a Project and Its Funding State

This section walks a real partner use case. The scenario: a 3rd-party explorer
site wants to render "Project page for `project_42`" showing project metadata,
on-chain vault state, whether the project is approved in the currently-active
grant round, the round summary, the project's current QF score and estimated
match, and recent contributors.

The partner uses the **Stellar wallet auth flow** from §2.2.2, but only because
it intends also to call write endpoints later; all GETs in this example are
public and work without a token.

export ROUND_ID=1   # discovered in step 2

that address.

### 7.8 Error handling during the flow

All steps above follow the standard error shape in §4. Two specific patterns the
explorer code should watch for:

1. **If step 3 (project) returns `SYS_005` (NOT_FOUND):** render a "Project does
   not exist or has been cancelled" page with HTTP 404 at the explorer layer.
   Do not show stale cached data.

2. **If step 4 or 5 returns `SYS_008` (rate limited):** the explorer must back
   off all calls to that base URL for at least `Retry-After` seconds, not just
   the grants routes — rate limit buckets are shared across the same client
   identity.

With those 7 steps, a partner has everything needed to render a full project and
funding state page, directly against the public backend, with no reliance on the
Lumenpulse webapp or its internal UI components.
